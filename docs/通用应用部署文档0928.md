# 通用应用部署文档

## 1. 文档目的

本文用于说明前后端分离应用上线前需要满足的条件、部署方需要提供的参数，以及部署完成后的验收标准。

本文不限定具体云平台、容器编排平台或部署流水线实现。部署平台负责完成镜像拉取、容器启动、服务发现、域名转发和 HTTPS 接入。

## 2. 适用的系统形态

适用于由一个或多个容器组成的 Web 应用，例如：

- 前端静态网站 + 后端 API 服务；
- 前端 SSR 服务 + 后端 API 服务；
- 单体 Web 服务；
- 后端附带异步任务服务或其他内部服务。

每个服务都应能够独立构建为容器镜像，并通过明确的端口提供服务。

## 3. 部署前必须满足的条件

### 3.1 镜像条件

- 每个服务已经构建为可运行的容器镜像；
- 镜像已经推送到部署平台可以访问的镜像仓库；
- 镜像仓库地址、镜像名称和版本标签准确无误；
- 建议使用不可变版本标签，例如 Git commit、Release 版本或构建编号，不建议生产环境只使用 `latest`；
- 容器启动命令已经写入镜像或由部署参数明确指定；
- 容器不应依赖开发机本地文件、宿主机目录或本地网络服务。

### 3.2 网络与端口条件

- 应用必须监听 `0.0.0.0`，不能只监听 `127.0.0.1` 或 `localhost`；
- 每个服务必须明确容器实际监听端口；
- 服务端口必须与镜像内应用实际监听端口一致；
- 后端访问数据库、对象存储、消息队列、第三方接口等外部依赖时，运行环境必须具备网络连通性；
- 应用之间不能使用 Docker Compose 中的固定服务名，应使用 Kubernetes Service DNS 或部署平台提供的内部服务地址；只有需要对公网提供服务时，才通过公网入口访问。

当前应用统一部署在 `vy-apps` Namespace。每个服务会创建独立的 Service，服务名格式为：

```text
<projectName>-<serviceName>
```

同一应用的服务之间可以通过以下地址访问：

```text
http://<projectName>-<serviceName>:<servicePort>
```

例如项目 `pom` 的后端服务名为 `pom-backend`，端口为 `8000`，其他集群内服务可以访问：

```text
http://pom-backend:8000
```

也可以使用完整的 Kubernetes DNS：

```text
http://pom-backend.vy-apps.svc.cluster.local:8000
```

浏览器端不能直接访问上述 Kubernetes 内部地址。前端应使用相对路径请求后端：

```text
/api
```

再由 Traefik Ingress 将 `/api` 转发到 `pom-backend:8000`。因此访问关系为：

```text
浏览器 -> https://pom.app.vayi.cn/api -> pom-backend:8000
服务端 -> http://pom-backend:8000
```

### 3.3 前端条件

静态前端需要包含用于提供静态文件的 Web 服务器，例如 Nginx、Caddy 或其他 HTTP Server。

前端 API 地址建议使用相对路径，例如：

```text
/api
```

不要把以下地址写入浏览器端代码：

```text
http://localhost:8000
http://backend:8000
```

生产环境通常通过同一个域名区分前端和后端：

```text
https://example.com/       -> 前端
https://example.com/api    -> 后端 API
```

如果前端容器内部配置了反向代理，代理目标必须使用部署平台中真实存在的后端服务地址。

### 3.4 后端条件

- 后端启动命令必须适用于生产环境；
- 后端必须监听 `0.0.0.0`；
- 后端端口必须与提交的 `containerPort` 一致；
- 后端不得把生产密钥、数据库密码、企微密钥等敏感信息写入镜像；
- 生产环境变量应由部署平台的运行时配置注入；
- 数据库迁移应作为独立的发布步骤管理，不应在每次容器启动时无条件执行破坏性迁移；
- 建议提供健康检查接口，例如 `/healthz` 或 `/readyz`。

如果应用在镜像构建阶段确实需要配置，应区分以下两类：

- 非敏感的构建参数，例如前端 API 前缀、公开环境标识、功能开关，可以通过 Docker `ARG` 或 GitHub Actions 环境变量传入；
- 私有依赖仓库凭据、签名密钥等敏感信息，应使用 Docker BuildKit Secret 临时挂载，不能通过 `ARG`、`ENV` 或构建命令写入镜像层；
- 数据库密码、运行时 Token、企微密钥等运行时敏感配置，仍应由 Kubernetes/Kestra 在容器启动时注入；
- 前端构建阶段写入 JavaScript 的配置最终会被用户看到，只能放公开配置，不能放任何密码或私密 Token。

例如，前端构建参数可以这样传递：

```dockerfile
ARG VITE_API_PREFIX=/api
ENV VITE_API_PREFIX=${VITE_API_PREFIX}
```

```yaml
- name: Build frontend
  uses: docker/build-push-action@v6
  with:
    context: ./frontend
    file: ./frontend/Dockerfile
    build-args: |
      VITE_API_PREFIX=/api
    push: true
    tags: ${{ env.FRONTEND_IMAGE }}
```

构建参数不会替代运行时配置。应用运行时仍应通过部署配置注入数据库、对象存储和第三方服务等环境变量。

### 3.5 域名与 HTTPS 条件

- 正式访问域名已经确定；
- 部署域名必须遵循 `*.app.vayi.cn` 域名范围。建议使用 `<项目名>.app.vayi.cn`，例如 `pom.app.vayi.cn`；
- 集群侧已经准备好域名 DNS 解析；
- 集群侧已经准备好 HTTPS 证书，且证书覆盖正式域名；
- 部署前只需检查域名解析和证书是否可用，不需要重复创建或申请；
- 前端和后端的跨域策略、Cookie 域、回调地址与正式域名一致；
- 企微、OAuth、支付等第三方平台的回调地址已经切换为正式 HTTPS 地址。

### 3.6 数据与外部依赖条件

部署前应确认：

- 数据库地址、端口、数据库名和账号已准备；
- 数据库允许部署环境访问；
- 对象存储、文件服务或消息服务已准备；
- 第三方服务的生产账号、密钥和回调配置已准备；
- 数据库、对象存储等数据已完成备份；
- 应用是否需要初始化数据或数据库迁移已经明确。

## 4. 部署方需要提供的参数

### 4.1 基础参数

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `projectName` | 是 | 应用或项目名称，建议使用小写字母、数字和短横线 |
| `host` | 是 | 对外访问域名，必须符合 `*.app.vayi.cn`，建议使用 `<projectName>.app.vayi.cn` |
| `tlsEnabled` | 平台配置 | 是否启用 HTTPS，生产环境通常应为 `true` |
| `tlsCertificate` | 平台配置 | 集群侧已有证书时无需提供，部署前只检查是否覆盖正式域名 |

### 4.2 服务参数

每个服务至少提供以下信息：

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 服务名称，例如 `frontend`、`backend` |
| `image.repository` | 是 | 镜像仓库地址 |
| `image.tag` | 是 | 镜像版本标签 |
| `containerPort` | 是 | 容器实际监听端口 |
| `servicePort` | 是 | 服务对内或对外提供的端口 |
| `expose` | 是 | 是否对公网暴露 |
| `path` | 对外服务必填 | 公网访问路径，例如 `/`、`/api` |

示例：

```json
{
  "projectName": "pom",
  "host": "pom.app.vayi.cn",
  "services": [
    {
      "name": "backend",
      "path": "/api",
      "image": {
        "repository": "registry.example.com/company/pom-backend",
        "tag": "sha-b2efc2d"
      },
      "expose": true,
      "servicePort": 8000,
      "containerPort": 8000
    },
    {
      "name": "frontend",
      "path": "/",
      "image": {
        "repository": "registry.example.com/company/pom-frontend",
        "tag": "sha-b2efc2d"
      },
      "expose": true,
      "servicePort": 80,
      "containerPort": 80
    }
  ]
}
```

### 4.3 运行时配置参数

运行时配置分为普通配置和敏感配置两类。

普通配置示例：

```text
APP_ENV=production
LOG_LEVEL=INFO
PUBLIC_BASE_URL=https://pom.app.vayi.cn
```

敏感配置示例：

```text
DATABASE_URL
WECOM_CORP_ID
WECOM_AGENT_ID
WECOM_SECRET
WECOM_TOKEN
WECOM_ENCODING_AES_KEY
MINIO_ACCESS_KEY
MINIO_SECRET_KEY
```

要求：

- 敏感配置由部署平台的 Secret 或安全配置中心注入；
- 不要把 `.env.production` 烘焙进镜像；
- 不要把真实密码、Token、Access Key 提交到 Git；
- 应用代码中的环境变量名称必须与部署参数名称一致；
- 配置变更后应重新发布或滚动重启对应服务。

## 5. 推荐部署流程

完整发布链路为：GitHub 发布新版本、GitHub Actions 自动构建镜像、镜像推送成功后自动触发部署。

### 自动化部署简版示例

镜像推送成功后，GitHub Actions 调用 Kestra Webhook，并根据返回的 `id` 查询部署状态：

```yaml
- name: Trigger Kestra deployment
  id: deploy
  env:
    KESTRA_WEBHOOK_URL: ${{ secrets.KESTRA_WEBHOOK_URL }}
  run: |
    response=$(curl --fail-with-body -sS -X POST "$KESTRA_WEBHOOK_URL" \
      -H "Content-Type: application/json" \
      --data-binary @deploy-payload.json)

    execution_id=$(echo "$response" | jq -r '.id')
    application_url="https://$(jq -r '.host' deploy-payload.json)"
    echo "Execution ID: $execution_id"
    echo "Application URL: $application_url"
    echo "execution_id=$execution_id" >> "$GITHUB_OUTPUT"

- name: Wait for deployment
  env:
    EXECUTION_ID: ${{ steps.deploy.outputs.execution_id }}
    KESTRA_USER: ${{ secrets.KESTRA_USER }}
    KESTRA_PASSWORD: ${{ secrets.KESTRA_PASSWORD }}
  run: |
    for i in $(seq 1 120); do
      result=$(curl --fail -sS \
        -u "$KESTRA_USER:$KESTRA_PASSWORD" \
        "https://kestra.vayi.cn/api/v1/main/executions/$EXECUTION_ID")
      state=$(echo "$result" | jq -r '.state.current')
      echo "Kestra state: $state"

      if [ "$state" = "SUCCESS" ]; then
        echo "Deployment succeeded: https://$(jq -r '.host' deploy-payload.json)"
        exit 0
      fi

      if [[ "$state" =~ ^(FAILED|CANCELLED|KILLED)$ ]]; then
        curl --fail -sS \
          -u "$KESTRA_USER:$KESTRA_PASSWORD" \
          "https://kestra.vayi.cn/api/v1/main/logs/$EXECUTION_ID" | jq .
        exit 1
      fi

      sleep 5
    done

    exit 1
```

其中 `deploy-payload.json` 是本次构建生成的部署参数，至少包含 `projectName`、`host` 和 `services`。详细的双服务完整 Workflow 见下方“完整 GitHub Actions 示例”。

### 阶段一：GitHub 发布新版本并触发 Action

1. 在 GitHub 创建并发布一个新 Release；
2. GitHub Actions 监听 Release Published 事件并自动启动；
3. 可额外保留 `workflow_dispatch`，用于人工重新执行构建和部署流程；
4. 普通代码 push 或 Pull Request 不应直接触发生产部署。

### 阶段二：构建并推送镜像

1. Action 检出 Release 对应的代码；
2. 使用本项目各服务对应的 Dockerfile 构建镜像；
3. 使用 Release 版本或 commit SHA 生成不可变镜像 tag；
4. 登录镜像仓库并推送本项目所有服务的镜像；
5. 确认本项目所有服务的镜像都推送成功。

### 阶段三：触发部署任务

1. Action 生成项目名称、访问域名、服务列表、镜像地址和镜像版本；
2. 检查集群侧已准备的域名 DNS、HTTPS 证书，并确认外部依赖可访问；
3. Action 读取 GitHub Secret `KESTRA_WEBHOOK_URL`；
4. 使用 POST 请求提交部署参数；
5. 部署平台根据参数创建或更新各服务；
6. 等待各服务启动并通过就绪检查；
7. 验证首页、API、登录、文件上传和第三方回调；
8. 记录本次发布使用的镜像版本、配置版本和验收结果。

#### 查询 Kestra 部署状态、日志并打印访问地址

Kestra Webhook 返回的执行对象中，`id` 就是本次部署的 `executionId`。Webhook 只负责创建异步任务，调用方需要继续查询执行状态：

```json
{
  "id": "4MXTkaha61BQ2w8jwl0G8m",
  "state": {
    "current": "CREATED"
  }
}
```

使用下面的接口查询执行状态：

```text
GET https://<kestra-host>/api/v1/main/executions/{executionId}
```

查询完整执行日志：

```text
GET https://<kestra-host>/api/v1/main/logs/{executionId}
```

实时跟踪日志：

```text
GET https://<kestra-host>/api/v1/main/logs/{executionId}/follow
```

状态含义：

```text
CREATED / RUNNING   执行中
SUCCESS             部署成功
FAILED              部署失败
CANCELLED / KILLED 任务被取消或终止
```

GitHub Actions 应在镜像推送成功后触发 Kestra任务，并轮询任务执行结果。

#### 完整 GitHub Actions 示例

下面示例适用于包含 `backend` 和 `frontend` 两个服务的项目。保存为项目仓库中的：

```text
.github/workflows/deploy.yml
```

其中 `backend/Dockerfile`、`frontend/Dockerfile`、项目名称和镜像名称需要根据实际项目修改：

```yaml
name: Build and Deploy

on:
  release:
    types: [published]

  workflow_dispatch:
    inputs:
      image_tag:
        description: "镜像版本，不填则使用当前 commit"
        required: false
        default: ""

env:
  REGISTRY: swr.cn-south-1.myhuaweicloud.com
  IMAGE_NAMESPACE: vayi
  PROJECT_NAME: new-project
  APP_HOST: new-project.app.vayi.cn
  KESTRA_API_URL: https://kestra.vayi.cn

jobs:
  build-and-push:
    name: Build and Push Images
    runs-on: ubuntu-latest

    outputs:
      image_tag: ${{ steps.meta.outputs.image_tag }}

    steps:
      - name: Checkout source
        uses: actions/checkout@v4

      - name: Generate image tag
        id: meta
        shell: bash
        run: |
          set -euo pipefail

          if [ -n "${{ github.event.inputs.image_tag || '' }}" ]; then
            image_tag="${{ github.event.inputs.image_tag }}"
          else
            image_tag="sha-${GITHUB_SHA::7}"
          fi

          echo "image_tag=$image_tag" >> "$GITHUB_OUTPUT"
          echo "Using image tag: $image_tag"

      - name: Login to SWR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ secrets.SWR_USERNAME }}
          password: ${{ secrets.SWR_PASSWORD }}

      - name: Build and push backend
        uses: docker/build-push-action@v6
        with:
          context: ./backend
          file: ./backend/Dockerfile
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAMESPACE }}/${{ env.PROJECT_NAME }}-backend:${{ steps.meta.outputs.image_tag }}

      - name: Build and push frontend
        uses: docker/build-push-action@v6
        with:
          context: ./frontend
          file: ./frontend/Dockerfile
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAMESPACE }}/${{ env.PROJECT_NAME }}-frontend:${{ steps.meta.outputs.image_tag }}

  deploy:
    name: Deploy to Kubernetes
    runs-on: ubuntu-latest
    needs: build-and-push

    steps:
      - name: Generate deployment payload
        env:
          IMAGE_TAG: ${{ needs.build-and-push.outputs.image_tag }}
        run: |
          set -euo pipefail

          jq -n \
            --arg projectName "${PROJECT_NAME}" \
            --arg host "${APP_HOST}" \
            --arg imageTag "${IMAGE_TAG}" \
            --arg backendImage "${REGISTRY}/${IMAGE_NAMESPACE}/${PROJECT_NAME}-backend" \
            --arg frontendImage "${REGISTRY}/${IMAGE_NAMESPACE}/${PROJECT_NAME}-frontend" \
            '{
              projectName: $projectName,
              host: $host,
              services: [
                {
                  name: "backend",
                  path: "/api",
                  image: {
                    repository: $backendImage,
                    tag: $imageTag
                  },
                  expose: true,
                  servicePort: 8000,
                  containerPort: 8000
                },
                {
                  name: "frontend",
                  path: "/",
                  image: {
                    repository: $frontendImage,
                    tag: $imageTag
                  },
                  expose: true,
                  servicePort: 80,
                  containerPort: 80
                }
              ]
            }' > deploy-payload.json

          jq . deploy-payload.json

      - name: Trigger Kestra deployment
        id: trigger
        env:
          KESTRA_WEBHOOK_URL: ${{ secrets.KESTRA_WEBHOOK_URL }}
        run: |
          set -euo pipefail

          response=$(curl --fail-with-body -sS \
            -X POST "$KESTRA_WEBHOOK_URL" \
            -H "Content-Type: application/json" \
            --data-binary @deploy-payload.json)

          echo "$response" | jq .

          execution_id=$(echo "$response" | jq -r '.id // .executionId')
          test -n "$execution_id"
          test "$execution_id" != "null"
          echo "execution_id=$execution_id" >> "$GITHUB_OUTPUT"

      - name: Wait for Kestra deployment
        env:
          EXECUTION_ID: ${{ steps.trigger.outputs.execution_id }}
          KESTRA_API_URL: ${{ env.KESTRA_API_URL }}
          KESTRA_USER: ${{ secrets.KESTRA_USER }}
          KESTRA_PASSWORD: ${{ secrets.KESTRA_PASSWORD }}
        run: |
          set -euo pipefail

          application_url="https://${APP_HOST}"
          echo "Kestra execution: $EXECUTION_ID"
          echo "Application URL: $application_url"

          for i in $(seq 1 120); do
            execution=$(curl --fail -sS \
              -u "$KESTRA_USER:$KESTRA_PASSWORD" \
              "$KESTRA_API_URL/api/v1/main/executions/$EXECUTION_ID")

            state=$(echo "$execution" | jq -r '.state.current')
            echo "Kestra state: $state"

            case "$state" in
              SUCCESS)
                echo "Deployment succeeded: $application_url"
                exit 0
                ;;
              FAILED|CANCELLED|KILLED|WARNING)
                echo "Deployment failed: $state"
                echo "Application URL: $application_url"
                curl --fail -sS \
                  -u "$KESTRA_USER:$KESTRA_PASSWORD" \
                  "$KESTRA_API_URL/api/v1/main/logs/$EXECUTION_ID" | jq .
                exit 1
                ;;
            esac

            sleep 5
          done

          echo "Timed out waiting for Kestra execution: $EXECUTION_ID"
          echo "Application URL: $application_url"
          exit 1
```

该 Workflow 需要配置以下 GitHub Actions Secrets：

```text
SWR_USERNAME
SWR_PASSWORD
KESTRA_WEBHOOK_URL
KESTRA_USER
KESTRA_PASSWORD
```

单服务项目可以删除另一个镜像构建步骤，并从 `services` 数组删除对应服务。`PROJECT_NAME` 和 `APP_HOST` 必须在项目之间保持唯一。

### 两个阶段之间的约束

- 只有 GitHub Release 发布后，才能自动启动生产发布流程；
- 只有本项目所有服务的镜像都构建并推送成功后，才能触发部署；
- 部署参数中的镜像 tag 必须与已推送的镜像 tag 完全一致；
- 镜像构建失败时不应触发部署；
- Helm 发布过程失败时由 `--atomic` 自动回滚；发布成功但业务验收失败时，使用上一个已验证镜像版本进行人工或流程化回滚，并保留失败日志；
- 镜像构建、镜像推送和应用部署是三个独立阶段，镜像推送成功不代表应用已经部署成功。

## 6. POM 项目部署示例

POM 仅作为本文的参数示例，不代表通用部署平台必须采用相同的项目结构。

POM 的完整发布流程为：发布 GitHub Release → GitHub Actions 自动启动 → 构建并推送 backend/frontend 镜像 → 读取 `KESTRA_WEBHOOK_URL` → 提交部署参数 → 完成应用部署。

POM 构建并推送两个镜像：

| 服务 | 镜像 |
| --- | --- |
| backend | `swr.cn-south-1.myhuaweicloud.com/vayi/pom-backend` |
| frontend | `swr.cn-south-1.myhuaweicloud.com/vayi/pom-frontend` |

例如使用同一个版本 tag：

```text
swr.cn-south-1.myhuaweicloud.com/vayi/pom-backend:sha-b2efc2d
swr.cn-south-1.myhuaweicloud.com/vayi/pom-frontend:sha-b2efc2d
```

镜像构建和推送成功后，通过部署平台提供的 Webhook 地址触发部署。POM 使用 GitHub Secret 保存完整地址：

```text
KESTRA_WEBHOOK_URL
```

仓库管理员需要在 GitHub 仓库的 `Settings -> Secrets and variables -> Actions` 中创建该 Secret：

- Name：`KESTRA_WEBHOOK_URL`
- Value：部署触发平台提供的完整 Webhook 地址

部署人员只需要有权限运行 GitHub Actions，不需要直接接触 Webhook 地址或其中的密钥。

## 7. 部署完成后的验收

### 7.1 基础验收

- 前端域名可以通过 HTTPS 访问；
- 首页静态资源加载正常；
- 浏览器没有明显的 404、502、跨域或混合内容错误；
- `/api` 请求可以到达后端；
- 后端健康检查接口返回成功；
- 所有服务实例处于运行状态；
- 日志中没有持续重启、端口占用、配置缺失或数据库连接错误。

### 7.2 业务验收

根据系统实际功能验证：

- 登录和权限校验；
- 核心查询和写入流程；
- 文件上传、下载和预览；
- 企业微信或其他第三方接口调用；
- 异步任务和消息通知；
- 数据库读写和关键数据一致性。

### 7.3 发布记录

每次发布至少记录：

- 项目名称；
- 发布时间；
- 前端镜像版本；
- 后端镜像版本；
- 配置变更说明；
- 数据库迁移情况；
- 验收结果；
- 回滚版本。

## 8. 常见问题排查

### 镜像拉取失败

检查镜像仓库地址、tag、仓库权限和部署环境网络。私有镜像必须提前配置镜像仓库凭据。

### 容器启动后立即退出

检查容器启动命令、环境变量、依赖服务连接、监听端口和应用日志。

### 前端显示 502 或 Nginx 报 upstream 错误

检查反向代理目标是否使用了部署平台中的真实服务地址，不要使用只在 Docker Compose 中存在的服务名。

### 首页正常但 API 失败

检查前端 API 基础路径、域名路由、后端路径前缀、跨域配置和认证 Cookie。

### 部署显示成功但应用不可用

部署成功只代表容器或服务完成发布，不等于业务验证成功。应继续检查日志、健康检查、服务地址和外部依赖。

## 9. 回滚要求

生产发布必须保留上一个可用镜像版本。出现严重问题时，应优先将服务切换回上一个已验证版本，并保留失败版本日志。

如果本次发布包含数据库结构变化，应提前确认数据库变更是否兼容回滚；数据库回滚不能简单等同于应用镜像回滚。
